# views/checkout

주문을 마치는 세 화면. 와이어프레임 `paym_001`·`paym_011`·`paym_002`에 대응한다.

| 파일 | 설명 |
| --- | --- |
| `ui/checkout-view.tsx` | 결제하기. 배송지·결제 정보·결제 방법 (`paym_001`) |
| `ui/checkout-view.test.tsx` | 결제 수단 고르기와 금액 표시를 본다 |
| `ui/checkout-address-view.tsx` | 배송지 설정 (`paym_011`) |
| `ui/checkout-done-view.tsx` | 주문 완료 (`paym_002`) |
| `ui/delivery-notice.tsx` | 언제 도착하는지 알리는 한 줄. 결제와 완료 두 화면이 쓴다 |
| `ui/pay-method-picker.tsx` | 결제 수단 고르기. 페이결제면 어느 페이인지 한 번 더 묻는다 |
| `index.ts` | 공개 API |

## 라우트

```text
/payment          결제하기
/payment/address  배송지 설정
/payment/done     주문 완료
```

**경로는 임시다.**

## 실제 결제는 붙이지 않았다

"결제하기"는 완료 화면으로 넘기기만 한다. 승인은 시크릿 키를 쥔 백엔드가 맡고, 금액 위변조 검증도 서버에서 한다. 결제 대행사와의 계약이 정해진 뒤에 잇는다.

사업자등록이 없어 실결제 자체가 아직 불가한 상태이기도 하다.

## 아직 없는 것

- 결제 수단의 `일반카드결제`는 카드 등록(`mypa_151`)과 맞물린다. 그 화면은 카드번호·CVC를 직접 받는 형태라 PCI DSS 확인 대기 중이다
- 결제상세의 "상품 옵션" 줄에는 금액이 들어간다. 시안 세 화면이 모두 그렇게 부르고 있어 그대로 옮겼고, "상품 금액"이 맞는지 PD팀에 확인을 요청해 뒀다
- 페이 세 곳은 로고 이미지가 없어 이름으로 그렸다
- 배송지 설정에서 고른 곳이 결제 화면에 반영되지 않는다. 화면 간 전달은 라우터 구조가 정해진 뒤에 붙인다
