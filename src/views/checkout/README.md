## 라우트

```text
/payment          결제하기
/payment/address  배송지 설정
/payment/done     주문 완료
```

**경로는 임시다.**

## 필수 동의 전에는 결제할 수 없다

시안(`paym_001`)이 결제하기 버튼 위에 다섯 줄을 둔다. 전체 동의 하나와 필수 셋, 선택 하나다. **문구에 대괄호가 붙는다** — `[전체 동의]`·`[필수] …`·`[선택] …`.

**필수 셋을 다 켜야 버튼이 풀린다.** 결제는 되돌릴 수 없는 동작이라, 동의 없이 눌리면 사용자가 무엇에 동의했는지 모르는 채로 돈이 나간다. 회색으로만 칠하지 않고 `disabled`로 막는 이유는 [component-convention](../../../docs/conventions/component-convention.md)의 "비활성은 `disabled` 속성으로 준다"를 따른 것이다.

약관 본문 링크는 아직 잇지 않았다. `/mypage/service/terms`가 있으나 마이페이지 하위라 결제 화면에서 접근하려면 공개 경로로 옮겨야 한다([routing.md](../../../docs/routing.md)의 확인 대기 항목).

## 결제 방법 자리는 시안을 따르지 않는다

시안이 라디오 다섯(간편결제·페이결제·일반카드결제·무통장입금·휴대폰)과 페이 로고 셋을 그렸지만 **그리지 않는다.** 그 자리는 토스 결제위젯이 차지한다 (#212). 섹션 제목과 여백만 시안에 맞추고 안쪽은 위젯에 맡긴다. 로고 에셋도 내려받지 않는다.

## 본문 글자색이 토큰과 어긋난다

시안이 제목과 값에 `#2a3038`을 쓰는데 그 값은 `surface/primary`(바닥색)다. **글자색 토큰 중에는 같은 값이 없다.** 우리가 앞서 올린 `mypa_061`·`mypa_161`·`paym_002`는 `#141414`(`text/body/default`)를 쓴다.

시안 hex 다섯 가지가 전부 토큰 값과 정확히 일치해 그대로 옮겼지만(`mypa_061` 때 세운 기준), **이 화면만 본문색이 다른 것이 의도인지 PD팀 확인 대상이다.**

## 배송 요청사항은 여섯 가지다

`paym_001_드롭다운`의 순서를 그대로 옮겼다. 마지막 `직접 입력`만 성격이 달라, 고르면 그 아래에 100자 칸이 열린다(`paym_001_직접입력`).

**고르는 칸의 높이를 `min-h-11`로 올린다.** 시안이 44px인데 shadcn `SelectTrigger`가 `data-[size=default]:h-8`로 32px을 못박아, 같은 속성(`h-*`)으로는 선택자 우선순위에 밀려 덮이지 않는다.

## 주문번호를 완료 화면에 남긴다

문의할 때 사용자가 대는 유일한 식별자다. 완료 화면에서 안 보여주면 주문 내역을 다시 찾아 들어가야 한다.

**주문번호와 주문 상세의 식별자가 같은 값인지는 아직 모른다.** API 계약이 정해질 때까지 목데이터에서 둘을 따로 둔다.

## 실제 결제는 붙이지 않았다

"결제하기"는 완료 화면으로 넘기기만 한다. 승인은 시크릿 키를 쥔 백엔드가 맡고, 금액 위변조 검증도 서버에서 한다. 결제 대행사와의 계약이 정해진 뒤에 잇는다.

사업자등록이 없어 실결제 자체가 아직 불가한 상태이기도 하다.

## 아직 없는 것

- 결제 수단의 `일반카드결제`는 카드 등록(`mypa_151`)과 맞물린다. 그 화면은 카드번호·CVC를 직접 받는 형태라 PCI DSS 확인 대기 중이다
- 결제상세의 "상품 옵션" 줄에는 금액이 들어간다. 시안 세 화면이 모두 그렇게 부르고 있어 그대로 옮겼고, "상품 금액"이 맞는지 PD팀에 확인을 요청해 뒀다
- 페이 세 곳은 로고 이미지가 없어 이름으로 그렸다
- 배송지 설정에서 고른 곳이 결제 화면에 반영되지 않는다. 화면 간 전달은 라우터 구조가 정해진 뒤에 붙인다

## 결제는 우리가 창까지, 승인은 백엔드가

토스 결제는 네 단계이고 마지막이 서버 일이다.

| | 하는 곳 |
| --- | --- |
| 결제 UI 렌더 · 결제 요청 · `successUrl` 복귀 | 브라우저 — 우리 |
| **승인 호출** (시크릿 키) | 서버 — 백엔드. **엔드포인트 미정** (#217) |

**시크릿 키가 브라우저에 닿으면 누구나 결제를 승인할 수 있다.** 2026-08-28 백엔드 협의에서 정리된 내용이다. `api/payment.ts`가 그 API를 부르는 자리이고 계약이 정해지면 그 안만 바뀐다.

**다만 어느 엔드포인트가 승인을 맡는지는 아직 없다.** API 명세의 결제 섹션은 두 줄뿐이다.

```text
POST /payments               결제        진행 중
GET  /payments/{paymentId}   결제 상세   시작 전
```

`POST /payments`가 준비와 승인을 겸하는지, 승인 자리가 따로 생기는지 백엔드 확인을 기다린다 (#217). **#212에서 `POST /payments/confirm`을 명세인 것처럼 적었는데 명세에는 그런 줄이 없다.** 서버에 그 경로가 실제로 있는지 없는지는 우리가 확인한 바 아니다 — 확인한 것은 명세에 적혀 있지 않다는 것까지다. 명세 행의 개정 전 내용이 "작성되어 있던 내용" 토글로 접혀 남아 있는데 그것을 현재 규격으로 읽은 것이 원인이다.

**결제수단 목록을 우리가 만들지 않는다.** 카드사·할부 개월·간편결제 분기를 위젯이 그린다. `component-convention`의 "외부 위젯이 그린다" 항목이다.

**실결제는 되지 않는다.** 사업자등록이 없어 테스트 키로만 돈다. `NEXT_PUBLIC_TOSS_CLIENT_KEY`는 브라우저에 노출되는 것이 정상이지만, **백엔드가 쓰는 테스트 상점의 결제위젯 클라이언트 키(`test_gck_`)를 받아 넣어야 한다.** 클라이언트 키와 승인용 시크릿 키는 한 상점의 세트라 짝이 안 맞으면 결제창은 떠도 승인에서 `INVALID_API_KEY`가 난다. 지금은 토스 문서의 공개 데모 키로 화면 확인만 한 상태다.

`orderId`는 지금 프론트에서 만든다. 원래 `POST /payments`가 줄 값인데 아직 "진행 중"이다.
