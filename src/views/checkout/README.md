## 라우트

```text
/payment          결제하기
/payment/address  배송지 설정
/payment/done     주문 완료
```

**경로는 임시다.**

## 필수 동의 전에는 결제할 수 없다

시안(`paym_001`)이 결제하기 버튼 위에 다섯 줄을 둔다. 전체 동의 하나와 필수 셋, 선택 하나다. **문구에 대괄호가 붙는다** — `[전체 동의]`·`[필수] …`·`[선택] …`.

**필수 셋을 다 켜야 버튼이 풀린다.** 결제는 되돌릴 수 없는 동작이라, 동의 없이 눌리면 사용자가 무엇에 동의했는지 모르는 채로 돈이 나간다. 회색으로만 칠하지 않고 `disabled`로 막는 이유는 [component-convention](../../../docs/conventions/component-convention.md)의 "비활성은 `disabled` 속성으로 준다"를 따른 것이다.

약관 본문 링크는 아직 잇지 않았다. `/mypage/service/terms`가 있으나 마이페이지 하위라 결제 화면에서 접근하려면 공개 경로로 옮겨야 한다([routing.md](../../../docs/routing.md)의 확인 대기 항목).

## 결제 방법 자리는 시안을 따르지 않는다

시안이 라디오 다섯(간편결제·페이결제·일반카드결제·무통장입금·휴대폰)과 페이 로고 셋을 그렸지만 **그리지 않는다.** 그 자리는 토스 결제위젯이 차지한다 (#212). 섹션 제목과 여백만 시안에 맞추고 안쪽은 위젯에 맡긴다. 로고 에셋도 내려받지 않는다.

## 본문 글자색이 토큰과 어긋난다

시안이 제목과 값에 `#2a3038`을 쓰는데 그 값은 `surface/primary`(바닥색)다. **글자색 토큰 중에는 같은 값이 없다.** 우리가 앞서 올린 `mypa_061`·`mypa_161`·`paym_002`는 `#141414`(`text/body/default`)를 쓴다.

시안 hex 다섯 가지가 전부 토큰 값과 정확히 일치해 그대로 옮겼지만(`mypa_061` 때 세운 기준), **이 화면만 본문색이 다른 것이 의도인지 PD팀 확인 대상이다.**

## 배송 요청사항은 여섯 가지다

`paym_001_드롭다운`의 순서를 그대로 옮겼다. 마지막 `직접 입력`만 성격이 달라, 고르면 그 아래에 100자 칸이 열린다(`paym_001_직접입력`).

**고르는 칸의 높이를 `min-h-11`로 올린다.** 시안이 44px인데 shadcn `SelectTrigger`가 `data-[size=default]:h-8`로 32px을 못박아, 같은 속성(`h-*`)으로는 선택자 우선순위에 밀려 덮이지 않는다.

## 주문번호를 완료 화면에 남긴다

문의할 때 사용자가 대는 유일한 식별자다. 완료 화면에서 안 보여주면 주문 내역을 다시 찾아 들어가야 한다.

**승인 응답에는 주문 상세로 갈 식별자가 없다.** 주는 것은 표시용 `orderNumber`(`ORD-…`)뿐인데 주문 상세 라우트는 숫자 id를 받는다. 승인 응답에 주문 id를 실어 줄 수 있는지 백엔드에 확인을 요청해 뒀다 (#256 리뷰).

## 결제 버튼 한 번에 세 단계가 이어진다

```text
[1] POST /orders    { addressId, items, deliveryNote }  → orderId (숫자 PK)
[2] POST /payments  { orderId }                         → tossOrderId (문자열)·orderName·customerKey
[3] requestPayment({ orderId: tossOrderId, orderName })  → 토스 결제창
```

**`[1]`을 화면이 열릴 때 부를 수 없다.** 본문에 배송 요청사항이 들어가 사용자가 고른 뒤라야 하고, 미리 부르면 결제하지 않고 떠난 주문이 쌓인다. 그래서 버튼을 누른 자리에서 셋을 잇는다.

**`orderId`가 두 개다.** `[2]`에 가는 것은 숫자 PK, 결제창과 승인에 가는 것은 문자열 주문번호(`ORD-…`)다. 이름이 비슷해 섞이면 위젯은 떠도 승인에서 막힌다.

**위젯에 `customerKey`를 넘기지 못한다.** 그 값은 `[2]`가 주는데 호출이 결제 버튼 뒤라, 위젯은 비회원(`ANONYMOUS`)으로 열린다. 승인은 `paymentKey`·`orderId`·`amount`로 이뤄져 통과한다.

**지금은 이것을 문제로 보지 않는다.** 회원으로 열어야 얻는 것은 저장해 둔 결제수단을 다시 쓰는 일인데, 사업자등록이 없어 실결제가 되지 않아 저장할 카드 자체가 없다. 약관의 "[선택] 다음 주문을 위해 이 결제 수단 저장"도 지금은 체크만 되고 어디에도 실리지 않는다.

**실결제를 붙일 때 다시 본다.** 그때 `GET /members/me` 같은 이른 API에 함께 실어 달라고 요청하거나, 위젯을 결제 버튼 뒤로 미뤄 `[2]`의 값으로 여는 두 갈래를 저울질한다. 코드는 이미 `customerKey`를 prop으로 받으므로 값만 꽂으면 된다 (#255).

**두 왕복이 걸려 버튼이 대기를 알린다.** 결제는 되돌릴 수 없어 두 번 눌리면 안 된다.

사업자등록이 없어 실결제 자체는 아직 불가하고 테스트 키로만 돈다.

## 승인이 실패하면 완료가 아니라 그 사실을 알린다

`successUrl`로 돌아왔다는 것은 **토스 결제창에서는 성공했다**는 뜻이다. 우리 서버 승인(`POST /payments/confirm`)에서 막힌 것이라 **돈이 빠져나갔을 수 있는 상태**다.

전에는 `page.tsx`가 승인을 부르다 던지면 Next.js 라우트 오류로 떨어져 "앗, 잠시 화면이 멈췄어요"가 났다. 결제와 무관해 보이는 문구이고, 무엇보다 **주문번호가 사라져 문의할 수단이 없었다** (#260).

지금은 라우트가 실패를 잡아 화면으로 넘긴다.

| | 하는 것 |
| --- | --- |
| 주문번호 | 토스가 복귀 쿼리에 실어 준 `orderId`를 크게 보이고 **복사 버튼**을 붙인다. 승인 응답이 없으니 화면이 댈 수 있는 식별자가 이것뿐이고, 문의에 붙이려면 옮겨 적지 않아도 되어야 한다 |
| 다음 행동 | **문의하기**와 **주문 내역 보기**. 다시 결제하러 가는 길은 주지 않는다 |
| 문구 | `payment.confirmFailed` · `payment.amountMismatch` |

**일반 실패 문구를 그대로 쓰지 않는다.** 네트워크 오류는 평소 "네트워크 상태를 확인해 주세요"로 떨어지는데, 이 화면에서 그 말은 다시 시도하라는 뜻으로 읽힌다. 결제창에서는 이미 성공한 뒤라 그 행동이 두 번 결제로 이어진다. 그래서 `payment.*`가 아닌 코드는 전부 승인 실패 문구로 모은다.

**시안에 없는 화면이다.** `paym_002`는 성공만 그린다. 오류 화면(`app/error.tsx`)과 같은 타이포·아이콘 크기로 조립했고 PD 확인 대상이다.

## 도착 예정일은 그리지 않는다

시안(`paym_001`)에 "지금 주문하면 모레(9/3) 도착해요" 한 줄이 있지만 **서버가 배송 예정일을 주지 않는다.** 시안 문구를 그대로 두면 오늘이 며칠이든 `9/3`이라 지난 날짜가 모든 주문에 뜬다 (#259 리뷰).

`delivery-notice.tsx`는 지우지 않고 둔다. 배송일을 받게 되면 그대로 되살린다.

**주문 완료(`paym_002`)에는 같은 문구가 아직 남아 있다.** 그쪽은 `MOCK`으로 명시된 자리라 승인 응답을 화면에 붙일 때 함께 본다.

## 실패하고 다시 누르면 주문이 새로 만들어진다

`[1]`이 성공한 뒤 `[2]`나 결제창에서 막히면 `catch`가 버튼만 되살린다. 다시 누르면 `[1]`부터 새로 타고, `createOrder`는 호출마다 새 `Idempotency-Key`를 보내므로 **서버에는 미결제 주문이 하나 더 남는다.**

**이것은 아는 채로 둔 것이다.** PM·FE가 "결제 실패 후 같은 주문 id로 재시도는 지원하지 않는다"로 범위를 정했고, 지금 고치려면 계약에 없는 것을 추측해야 한다 — 실패한 주문이 어떤 상태가 되는지, 같은 `Idempotency-Key`가 원래 주문을 돌려주는지 아니면 거부하는지 (#259 리뷰).

**실결제를 붙일 때 백엔드에 두 가지를 확인한다.**

- 미결제 주문의 수명과 정리 주체
- `preparePayment` 실패 후 같은 주문을 재시도할 수 있는지

`Idempotency-Key`를 호출마다 새로 만드는 것은 의도한 것이다. 그 키는 **한 번의 결제 시도 안에서** 네트워크 재시도가 일어나도 주문이 두 건 생기지 않게 하는 장치이고, 사용자가 실패를 보고 다시 누르는 것은 다른 시도다.

## 배송지는 기본 배송지를 쓴다

`/payment/address`에서 고른 결과를 결제 화면으로 돌려보낼 경로가 없다. **회원가입·온보딩 어디에도 배송지를 입력받는 화면이 없고**(`sign_*` 여섯 · `onbo_*` 전부 확인), 시안이 `paym_011`에 `기본 배송지` 뱃지만 두고 "이 주소로 배송" 같은 확정 버튼을 그리지 않았다.

그래서 `isDefault`인 곳을 싣는다. 기본이 지정되지 않은 계정은 목록 맨 앞을 쓴다 — 조회가 기본을 앞으로 정렬한다.

**등록된 곳이 하나도 없으면 `empty_dilivery 2`(`2022:157931`)대로 등록하러 보낸다.** 우측 링크가 `배송지 변경`에서 `배송지 등록`으로 바뀌고 `/mypage/address/new`로 간다.

**"이번 주문만 다른 곳으로"는 안 된다.** 시안에 그 수단이 없어 PD 확인 항목이다.

## 결제할 줄은 장바구니에서 고른 것이다

장바구니가 `?items=NORMAL:1,TIME_DEAL:3`으로 넘긴다. 넘기지 않으면 결제 화면이 장바구니 전체를 세어 **고르지 않은 것까지 결제된다.**

쿼리가 없으면 살 수 있는 줄 전부를 본다 — 주소창으로 바로 들어와도 화면이 성립해야 한다. **살 수 없는 줄(`available: false`)은 언제나 뺀다.** 이름·금액이 전부 `null`이라 셀 수도 주문에 실을 수도 없다.

**배송비는 3,000원 고정이다.** 장바구니와 같은 값이고, 응답에 `deliveryFee`가 없어서다 (#214).

## 아직 없는 것

- 결제 수단의 `일반카드결제`는 카드 등록(`mypa_151`)과 맞물린다. 그 화면은 카드번호·CVC를 직접 받는 형태라 PCI DSS 확인 대기 중이다
- 결제상세의 "상품 옵션" 줄에는 금액이 들어간다. 시안 세 화면이 모두 그렇게 부르고 있어 그대로 옮겼고, "상품 금액"이 맞는지 PD팀에 확인을 요청해 뒀다
- 페이 세 곳은 로고 이미지가 없어 이름으로 그렸다
- 배송지 설정에서 **고른 곳을 결제 화면으로 돌려보내지 못한다.** 고르는 API가 없고 시안에 확정 버튼도 없어, 결제 화면은 기본 배송지를 쓴다(위 절)
- **시안의 "주소를 아직 안 넣은 회사 자리"는 그리지 않는다.** 등록 API가 주소를 필수로 받아 빈 자리가 만들어지지 않는다. 집·회사는 서버에 없는 개념이고 우리가 `addressName`으로 아이콘만 고른다 — PD 확인 대상이다

## 결제는 우리가 창까지, 승인은 백엔드가

토스 결제는 네 단계이고 마지막이 서버 일이다.

| | 하는 곳 |
| --- | --- |
| 결제 UI 렌더 · 결제 요청 · `successUrl` 복귀 | 브라우저 — 우리 |
| **승인 호출** (시크릿 키) | 서버 — 백엔드. `POST /payments/confirm` (#255) |

**시크릿 키가 브라우저에 닿으면 누구나 결제를 승인할 수 있다.** 2026-08-28 백엔드 협의에서 정리된 내용이다. `api/payment.ts`가 그 API를 부르는 자리다.

**승인 경로는 2026-09-18 팀장 회의에서 확정됐다.** 한때 `POST /payments`가 준비와 승인을 겸하는지 몰라 막혀 있었는데, 결제 섹션이 세 줄로 갈렸다.

```text
POST /payments           결제 요청  [2]
POST /payments/confirm   결제 승인  [5]
GET  /payments/{id}      결제 상세  시작 전
```

**아직 토스와 실제로 주고받은 적이 없다.** 백엔드가 "결제 요청부터 DB 반영까지는 확인했지만 토스와는 못 해봤다"고 밝혔다 — 프론트 코드가 없어 승인 구간을 테스트하지 못한 것이라, **우리가 붙이는 순간이 첫 실측**이다. 처음 한 번은 실패를 전제로 본다.

**결제수단 목록을 우리가 만들지 않는다.** 카드사·할부 개월·간편결제 분기를 위젯이 그린다. `component-convention`의 "외부 위젯이 그린다" 항목이다.

**실결제는 되지 않는다.** 사업자등록이 없어 테스트 키로만 돈다. `NEXT_PUBLIC_TOSS_CLIENT_KEY`는 브라우저에 노출되는 것이 정상이지만, **백엔드가 쓰는 테스트 상점의 결제위젯 클라이언트 키(`test_gck_`)를 받아 넣어야 한다.** 클라이언트 키와 승인용 시크릿 키는 한 상점의 세트라 짝이 안 맞으면 결제창은 떠도 승인에서 `INVALID_API_KEY`가 난다. 지금은 토스 문서의 공개 데모 키로 화면 확인만 한 상태다.
