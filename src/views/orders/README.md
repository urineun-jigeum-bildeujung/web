## 2026-09-23 시안 (#405)

| 자리 | 그리는 것 |
| --- | --- |
| 묶음 | **결제일로 묶고 그 안을 결제 시각으로 나눈다** — "결제일 26.09.03" 머리 아래 주문마다 "09.03 19:34" · "주문 상세" 링크. 옛 "자세히 보기" 버튼 자리를 링크가 대신한다 |

| 뱃지 색 | 배송준비중 회색, 배송중 파랑, 배송완료·구매확정 초록. 그전 시안은 넷이 같은 색이었다 |
| 버튼 | 배송준비중 "주문 취소"+"장바구니 담기", 배송중 "배송 위치 보기"+"장바구니 담기", 그 뒤로는 "장바구니 담기" |
| 결제일 사이 | 구분선(`border/default`). 같은 날 주문 사이에는 넣지 않는다 |

PD팀이 시안 옆에 남긴 메모(`mypa_061 레이아웃 변경 참고` 구역, `3326:33777`)가 위 표의 근거다 — 세그먼트 추가, 결제일 묶음과 결제 시간 나눔, 날짜 사이 구분선, "자세히 보기" → "장바구니 담기".

**결제일로 묶는 것은 이어서 오는 같은 날뿐이다.** 서버가 최신순으로 주고 다음 쪽도 그 뒤를 이어 같은 날은 늘 붙어 온다. 목록에 결제 시각이 없어 주문 시각으로 묶는다 — 결제는 주문을 만든 직후라 날짜가 같다.

**상태와 행동은 상품마다 그리지만 서버에서는 주문 단위다.** 목록 응답에 상품별 상태가 없고 취소·구매 확정도 주문에 걸려 있어, 같은 주문의 상품은 늘 같은 뱃지를 달고 어느 줄에서 "주문 취소"를 눌러도 주문 전체가 취소된다. **PD팀은 상품마다 따로 취소하는 것이 맞다고 답했다(2026-09-23).** 서버에 상품 단위 취소가 없어 백엔드 요청 대상이다.

**"구매확정 하기" 버튼은 처음 정리본에서 빠졌다가 다시 들어왔다.** PD팀이 누락이라 답하고 넣었다(2026-09-23). 문구의 띄어쓰기도 시안 그대로다. 시트는 그 주문의 상품을 모두 보인다 — 확정이 주문 단위라서다.

## API

`GET /orders`로 받는다. 커서 페이지네이션(`size`·`cursor` → `nextCursor`·`hasNext`)이고
**목록 끝이 화면에 들어오면 다음 쪽을 이어 부른다.** 한 번에 오는 것이 기본 열 건이라
첫 쪽만 그리면 열한 번째 주문부터 볼 길이 없다 (#288).

**"더보기" 버튼 대신 스크롤로 잇는다.** 시안(mypa_061)에 버튼 자리가 없어서다.
`nextCursor`는 백엔드가 `Base64(orderedAt + ":::" + orderId)`로 만든 값이라 받은 그대로
다시 보낸다. **멈추는 조건이 둘이다** — `hasNext`가 참이어도 커서가 없을 때, 그리고 **방금 보낸
커서가 그대로 돌아왔을 때**다. 둘 다 막지 않으면 같은 쪽을 끝없이 부르며 같은 주문이 쌓인다.

**다음 쪽 실패는 첫 조회 실패와 다르게 다룬다.** 첫 조회가 실패하면 화면을 오류로 덮지만,
둘째 쪽부터 실패하면 이미 받은 주문을 그대로 두고 목록 아래에 다시 시도 버튼만 붙인다 —
보고 있던 목록이 사라지면 스크롤하던 자리를 잃는다. 실패한 동안에는 관찰도 멈춘다.
저절로 다시 부르면 같은 실패가 되풀이된다 (#294 리뷰).

구매 확정·주문 취소는 `204 No Content`라 바뀐 주문을 응답으로 받지 못한다. 끝난 뒤 목록을
다시 조회해 맞춘다. **낙관적으로 먼저 그리지 않는다** — 되돌릴 수 없는 동작이라 서버가 거절하면
확정된 줄 알았던 주문이 되살아난다 (#284).

## 아직 없는 것

**서버에 없어 막힌 넷** — 팀장이 백엔드에 요청할 목록에 넘겼다 (#405).

**탭 이름은 "취소·반품·교환"이다.** 시안 안에서 목록 프레임·PD 메모는 "취소·환불·교환", 둘째 탭 프레임은 "취소·반품·교환"으로 갈려 물었더니 PD팀이 뒤의 것으로 확정했다(2026-09-23). 메모는 PD팀이 고친다.

| 자리 | 없는 것 | 받기 전까지 |
| --- | --- | --- |
| 상품마다 금액 | 목록 응답 `ItemSummary`는 `orderItemId`·`thumbnailUrl`·`productName`·`quantity`뿐이다 | 금액 줄을 그리지 않는다. `0원`으로 그리면 공짜로 산 것처럼 보인다 |
| 상품마다 "주문 취소" | 서버 `POST /orders/{orderId}/cancel`은 주문 전체만 취소한다 | 어느 줄에서 눌러도 주문 전체가 취소된다. 확인창 제목도 "주문을 취소할까요?"다 |
| "장바구니 담기" | 담기 요청은 `{ itemType, itemId, quantity }`인데 주문 응답(목록·상세 모두)에 상품 ID·`itemType`이 없다 | 누르면 준비 중 안내(팀장 결정 2026-09-23) |
| "취소·반품·교환" 탭 | 탭 화면 시안은 있다(`mypa_061_취소·반품·교환` `3326:33002` — 신청 건마다 접수일·"환불" 같은 뱃지·상품·자세히 보기). **신청 건을 모아 주는 API가 없다** | 준비 중 화면. 취소한 주문은 지금처럼 주문내역 탭에 남는다 |

**상품 옵션은 없는 것이 맞다.** 시안의 둘째 줄이 그 자리인데 백엔드에 옵션이라는 데이터가
없다. PD팀이 "옵션은 빼고 수량은 있어도 괜찮다"고 확인해 줘서 몇 개를 샀는지 넣는다 (#297).

**다섯 상태를 모두 옮긴다.** 2026-09-21에 백엔드 `OrderStatus` enum에서 값을 확인해
`PREPARING`·`SHIPPING`까지 채웠다 (#288). 취소·환불된 주문은 시안에 뱃지가 없어 그대로 두었고,
그런 값이 오면 뱃지 없이 "장바구니 담기"와 머리의 "주문 상세" 링크만 남는다. 자세한 것은
[entities/order](../../entities/order/README.md)를 본다.

**배송 조회.** 시안은 `배송 위치 보기`를 활성으로 그렸지만 택배사 연동이 정해지지 않아
준비중 안내만 띄운다. 갈 곳이 생기면 `preparing-dialog.tsx`를 거치지 않게 그 자리를 잇는다 (#201).
