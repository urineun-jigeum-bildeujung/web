# views/onboarding

반려동물 프로필을 등록하는 온보딩 화면. Figma `UI` 페이지의 `onboarding` 행(`onbo_001`~`onbo_005`, `onbo_011`)에 대응한다. 이 저장소에서 UI 시안을 처음 구현한 화면이라 공용 컴포넌트의 시안 모양이 여기서 정해졌다.

**체구를 고르면 몸무게와 체질 항목이 그 자리에 나타난다.** 시안이 `onbo_003_체구선택전`과 `체구선택후` 두 장으로 나뉘어 있는 이유다. **고양이는 체구를 묻지 않는다**(#391) — 그 질문을 통째로 빼고 몸무게·체질은 바로 묻는다. 요청에도 `size`를 싣지 않는다.

## 라우트

`/onboarding` — `src/app/onboarding/page.tsx`

UCS의 최초 서비스 소개와 IA의 프로필 등록 온보딩 정의가 달라 화면 개념은 PM·PD 확인이 필요하다. 현재 `/onboarding`은 반려동물 프로필 등록 흐름으로 사용한다.

## 상태를 어디에 두었나

| 대상 | 위치 | 이유 |
| --- | --- | --- |
| 현재 단계 | URL 쿼리 `?step=` | 새로고침·뒤로가기에서 살아남아야 한다. 단계 전환은 `push`지만 등록 성공 → 완료는 `replace`로 바꿔 끼우고 홈도 `replace`로 간다 — 홈에서 뒤로가기가 완료 단계로 돌아오지 않게(#371). 앞 입력 단계 항목은 남는다 |
| 입력값 | 기기(`localStorage`) | 새로고침해도 남아야 한다. 서버 저장은 프로필 등록 API가 정해져야 한다 |
| 들어온 화면 | URL 쿼리 `?from=` | 아이 추가 자리(메인·마이페이지·아이 관리)가 싣는다. 첫 입력 단계의 "이전"이 그리로 돌아간다(#527). 가입 직후 첫 등록에는 없다 |

`@use-funnel`을 검토했지만 쓰지 않았다. `@use-funnel/next`의 `useNextRouter`가 `next/router`(Pages Router)를 반환해 App Router에서 동작하지 않는다. 이미 도입한 `nuqs`로 같은 일이 되고 "새로고침에 남아야 하는 상태는 URL"이라는 규칙과도 맞는다.

**진행 표시는 입력 단계 셋만 센다.** 도입부·품종 선택·완료를 넣으면 사용자가 보는 진행률이 실제와 어긋난다.

## 아직 없는 것

프로필 저장 API 연동. 백엔드 계약이 정해지면 `done` 단계 진입 전에 붙인다. 지금은 마지막 단계에서 바로 완료 화면으로 넘어간다.

## 짚어둘 것

**입력값은 기기에 남긴다.** 단계는 URL에 있는데 입력값이 컴포넌트 상태였을 때, `?step=health`로 새로고침하면 단계만 남고 종이 기본값으로 돌아가 **고양이 보호자가 강아지 질환 갈래를 만났다.** 유즈케이스 시트가 "입력 중이던 정보를 저장하고 이어서 진행"을 우선순위 높음으로 적고 있다. 서버에 남기는 것은 프로필 등록 API가 정해져야 해서 그때까지 `model/draft-storage.ts`가 맡는다.

**사진은 기기에 남기지 않는다.** `File`은 직렬화되지 않는다. base64로 바꾸면 `localStorage` 용량(5MB)에 걸리고, 다시 고르는 것이 한 번의 탭이라 그대로 둔다.

**단계를 오갈 때는 사진이 남는다(QA 온보딩, #602).** 파일은 초안 캐시(메모리)에 있고, 첫 단계가 그것을 `AvatarUploader`의 `file`로 넘겨 미리보기를 되살린다. 미리보기 주소가 업로더 안의 상태뿐이던 때는 두 번째 단계에서 "이전"을 누르면 빈 원이 됐다 — 파일은 초안에 남아 등록 때 올라가는데 화면만 사진이 빠진 것처럼 보였다. 주소(`blob:`)는 첫 단계가 화면에서 빠질 때 거둔다.

**새로고침 뒤에는 사진을 되살리지 않는다.** 메모리의 초안이 사라지고 기기에는 사진이 없어, 초안의 `photo`도 `null`이다. 빈 원이 보이는 것이 등록될 내용과 같다 — 화면과 등록이 어긋나지 않는다. 새로고침 뒤까지 남기려면 IndexedDB처럼 `Blob`을 담는 저장소가 필요한데, 비동기로 읽어 초안보다 사진이 늦게 뜨고 등록·이탈 때 지우는 것도 따로 챙겨야 한다. 다시 고르는 한 번의 탭에 비해 커서 두지 않았다.

**저장된 값은 한 칸씩 확인해 옮긴다.** 통째로 펼치면 손으로 고친 값이나 옛 형식이 그대로 들어와 나중에 엉뚱한 곳에서 깨진다.

**화면 안에서 온보딩을 떠나는 길이 없다.** 시안에 건너뛰기도 닫기도 없고, 섹션 메모가 "건너뛰기, 닫기 버튼 삭제"라고 적고 있다. 회원가입 직후 반드시 거치는 단계라는 뜻으로 읽힌다. 기기 뒤로가기 말고는 나갈 방법이 없다는 점은 PD 확인 대상으로 남겨 둔다. 첫 입력 단계의 "이전"도 시안대로 잠겨 있어 도입부로 되돌아가지 않는다.

**아이 추가로 들어왔을 때만 첫 입력 단계의 "이전"이 열린다(QA No.254, #527).** 추가 자리가 `?from=`에 자기 화면을 실어 보내고, "이전"은 그 화면으로 `replace`한다 — 쌓으면 그 화면의 뒤로가기가 다시 입력 단계로 온다. **`router.back()`을 쓰지 않는다.** 단계 이동이 모두 `push`라 상세에서 "이전"으로 돌아온 첫 단계에서 한 칸 되돌리면 상세로 가고, 버튼만으로는 빠져나갈 수 없는 고리가 된다. 배송지 폼의 `from`(#369)과 같은 해법이다. 주소창에 실려 오는 값이라 `entities/pet`의 `ADD_PET_ORIGINS`에 적은 세 곳만 받고, 그 밖의 값이면 가입 직후처럼 잠긴다. 완료 화면에서 "프로필 추가"로 다시 돌아도 `from`이 주소창에 남아 같다.

**아이는 5마리까지 들인다(QA No.130, #527).** 등록한 아이 수를 받아 5마리면 완료 화면의 "프로필 추가"와 그 권유 문구("함께할 다른 가족이 더 있나요?"·"반려동물이 더 있다면…")를 뺀다. 그 경우의 시안이 없어 새 문구를 만들지 않고 권유만 덜었다. 추가 자리는 모두 사라지지만 주소로 첫 입력 단계에 바로 들어올 수 있어, 그때는 입력칸과 진행 표시 대신 `PetLimitStep` 안내를 보인다. **첫 입력 단계만 막는다.** 상세·건강 단계까지 막으면 다섯째를 등록한 직후 목록이 먼저 갱신될 때 건강 단계에 안내가 한 번 비칠 수 있다. 백엔드 등록에 개수 검사가 없어 주소로 상세·건강 단계에 들어오면 여전히 여섯째가 등록될 수 있다.

**품종은 검색해서 고른다.** 시안(`onbo_011`)이 검색창과 결과 목록뿐이고 확인 버튼이 없다. 검색 전에는 종별 전체 목록을 보이고, 줄을 누르면 바로 상세 단계로 돌아간다. 품종 선택 단계에는 진행 표시 대신 머리말이 있다.

**완료 화면의 "프로필 추가"는 같은 흐름을 다시 돈다.** 시안에 이어지는 화면이 없어 초안을 지우고 첫 입력 단계로 보낸다.

**몸무게 예시는 품종이 아니라 종·체구로 가른다.** 시안은 "말티즈의 평균 몸무게는 5kg이에요"처럼 품종별 평균을 적는데, 품종 조회와 서버 품종 표에 체중이 없다. 강아지는 고른 체구의 범위(`SIZE_GUIDE`와 같다), 고양이는 종 하나의 범위를 보인다(#524). 고양이 범위(3~5kg)는 PD 확정값이 아니다.

**건강 정보는 목록에서 고른다.** 자유 입력이면 보호자마다 다르게 적어 같은 질환이 여러 표기로 쌓이고, 그 값으로는 추천을 만들 수 없다. 시트는 `entities/pet`의 `HealthPickerSheet`이고 질환·알러지가 목록만 바꿔 같은 것을 쓴다.

**목록은 아직 더미다.** 시안의 칩이 목 데이터였다 — 관절 탭 다섯 중 넷이 "고관절 이형성증"으로 복붙돼 있다. 탭 여섯은 확정이라 그대로 따르고 항목만 통용되는 분류로 채웠다. 실제 목록이 오면 `entities/pet/model/health.ts` 한 파일만 갈아끼운다.

**체형 안내는 시트, 체구 안내는 말풍선이다.** 체형(BCS)은 다섯 단계를 그림과 설명으로 나열해야 해서 시트이고, 체구는 세 줄이라 물음표를 눌러 여닫는 말풍선(Popover)이다. 둘 다 hover가 아니라 눌러서 연다.

**"작성 완료"에서 서버에 등록된다.** 그전까지는 초안이 기기에만 남는다. 화면 값과 API 값의 모양이 거의 다 달라(성별·중성화·종·체구의 표기, 체형 0~4 → 1~5, 자유 입력인 나이·몸무게·생일) 옮기는 자리를 `model/to-register-request.ts`로 뺐다. 화면 안에 두면 테스트할 수 없다.

**등록에 실패하면 초안을 지우지 않는다.** 지우면 여섯 단계를 처음부터 다시 채워야 한다. 완료 화면으로도 보내지 않는다 — 등록되지 않았는데 됐다고 알리는 셈이다.

**사진은 등록 훅이 먼저 올린다.** 요청의 `image`는 URL이라 `shared/api/upload-image`로 S3에 올린 뒤 그 주소를 싣는다. 훅 안에서 하므로 "작성 완료"의 대기 표시가 업로드 시간까지 덮는다(#269). 새로고침으로 초안을 되읽으면 사진은 없다 — `File`은 기기에 남기지 않는다.

**잘못 적은 값은 칠 때 걸러 내고 그래도 어긋나면 알린다.** 이름은 이모티콘이 빠지고(숫자는 받는다) 10자에서 멈추며(#602), 나이는 숫자 두 자리까지, 몸무게는 숫자와 소수 첫째 자리까지만 들어가며 값 뒤에 단위가 붙어 `4.5kg`으로 보인다. 생년월일은 치는 대로 `0000. 00. 00`으로 맞춰진다. 그래도 `2003. 10. 92`처럼 달력에 없는 날이나 상한(30살)을 넘는 나이는 만들 수 있어 그때는 입력칸 아래에 알리고 다음 단계로 못 가게 막는다. **이 규칙은 정보 수정과 같다** — `entities/pet`의 `profile-input`·`parse-profile-input`·`WeightField` 한 곳에 있다(#524).

**개월 단위로는 적을 수 없다.** 시안(`onbo_003`)의 나이 칸은 `0살`·`4살`로 살 단위뿐이고 서버도 나이를 1 이상의 정수로 받는다. 1살 미만 아이를 어떻게 적게 할지는 PD 확인 대상이다(#524).

**나이와 생일이 어긋나도 막지 않는다.** 시안이 생일 칸에 "처음 만난 날을 적어도 좋아요"라고 안내해, 생일로 나이를 따지면 그 안내대로 적은 사람이 막힌다.

**조용히 빠지게 두지 않는 이유가 있다.** 잘못 적은 칸을 그냥 빼고 보내면 사용자는 적었으니 저장된 줄 안다. 생일이 달력에 없는 날이면 서버가 본문을 통째로 거절해(`Failed to read request`) 등록 자체가 막히기까지 한다.
