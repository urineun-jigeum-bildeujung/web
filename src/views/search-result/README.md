# search-result

검색어에 걸린 상품을 2열로 보여준다. 정렬을 고를 수 있고, 그냥 검색하러 왔으면 카드마다 할인율·별점·찜하기를 담아 보여주지만, 비교 자리를 채우러 왔으면 체크만 하면 되니 이름·가격만 남긴다.

- **라우트**: `/search/result?q=...` — `src/app/search/result/page.tsx`
- **조립**: `widgets/bottom-nav` · `shared/ui`의 `product-grid-card` · `rating` · `select` · `bottom-action-bar` · `button`
- **상태**: 검색어(`q`)와 정렬(`sort`) 모두 URL 쿼리. 상품 목록은 서버 상태이나 API 계약 확정 전 미연동
- **참고**: UI 시안 기준(#245, 2396-80432 일반 검색·1117-6424 비교 고르기)

| 파일 | 설명 |

| `ui/search-result-view.tsx` | 화면 조립 |

## 짚어둘 것

**검색 입력 화면과 슬라이스를 나눴다.** 머리말 동작이 반대라서다. `/search`는 들어오자마자 입력창에 초점을 주는 화면이고, 여기 검색바는 **입력창처럼 보이는 버튼**이라 누르면 `/search`로 되돌아간다. 한 라우트에서 `q` 유무로 갈래를 나누면 한 파일이 두 화면을 담게 되고, 되돌아갈 때 `q`를 지워야 해서 오히려 복잡해진다.

**정렬 목록이 메인과 다르다.** IA의 검색 결과 행이 `추천순(기본) · 인기순 · 낮은 가격순 · 높은 가격순 · 리뷰 많은순`으로 따로 적고 있다. 메인은 리뷰 높은/낮은 순을 쓴다. 같아 보인다고 합치지 않는다.

**정렬은 히스토리에 쌓지 않는다.** 같은 목록을 좁히는 것이라 쌓이면 뒤로가기를 여러 번 눌러야 화면을 떠난다. 검색어는 반대로 화면 구성을 통째로 바꾸므로 `/search`에서 `push`로 들어온다.

**정렬은 목업 단계라 화면에서 한다.** 연동하면 검색어와 정렬을 요청 파라미터로 넘겨 서버가 걸러 주고, 이 자리의 비교 함수는 통째로 사라진다 — 서버가 할 수 있는 일을 화면에서 다시 하지 않는다는 [AGENTS.md](../../../AGENTS.md) 2.5절 때문이다. 다만 `sort`를 손에 쥐고 아무것도 하지 않으면 고를 수는 있는데 순서가 그대로인 죽은 UI가 된다.

**빈 결과일 때는 개수와 정렬도 감춘다.** 셀 것이 없는데 "총 0개"와 정렬을 남겨 두면 고를 수 있는 것처럼 보인다.

**결과가 없을 때는 공용 `EmptyState`를 쓰지 않는다.** 그 컴포넌트는 72px 아이콘·18px 굵은 제목·14px 설명 두 단으로 나뉜 시안(메인 타임딜 빈 상태) 기준인데, 이 화면(2022-157694)은 굵기 구분 없는 16px 문단 한 덩어리(3줄)다. `NoResults`로 로컬에 따로 그린다 — `views/search`의 "최근 검색어 없음"과 같은 이유다.

**적합도를 재지 못한 상품은 어떤 정렬에서도 마지막이다.** 유즈케이스 시트(상품 탐색 6-1)가 그렇게 적고 있다. 점수를 모르는 상품이 가격순 첫 줄에 오면 무엇을 기준으로 고르는지가 흐려진다. 정렬 비교 함수보다 이 판정이 먼저다. `matchScore`는 화면에 배지로 그리지 않아도 이 정렬 판정에는 그대로 쓰인다.

**비교 자리를 채우러 왔으면(`slot` 있음) 카드를 눌러도 이동하지 않는다.** Figma(#245, 1117-6424)가 카드에 체크박스를 그린다 — `ProductGridCard`의 기존 `selectable`을 그대로 쓴다. 대신 하단이 `BottomNav`가 아니라 `BottomActionBar`의 "선택 완료" 버튼으로 바뀌고, 눌러야 비로소 `/compare`로 간다. Figma 프레임에 하단 네비게이션이 없어 고르는 중엔 다른 탭으로 새지 않게 한다.

**비교 자리를 채우러 왔으면 카드뿐 아니라 "총 N개"·정렬 자체가 없다.** 처음엔 일반 검색 카드에 적합도 배지만 얹으면 될 거라 짐작했는데, Figma(1117-6424)를 다시 정확히 조회하니 총 개수·정렬 행 자체가 없고 카드도 이미지+체크박스, 이름, 가격만 있다 — 할인율·별점·적합도가 전부 빠져 있다. 체크하고 확정하는 것 자체가 목적이라 무엇이 더 맞는지·싼지는 이 화면이 답할 질문이 아니다.

**`GeneralResultList`·`PickingResultList`로 완전히 나눠 그린다.** `ProductGridCard` 하나에 `picking ? A : B` 삼항 prop을 여러 개(적합도·할인율·별점·찜하기·가격 크기) 쌓았다가, 그중 하나를 빠뜨려 비교 화면에 적합도 배지가 새는 사고가 났다. [component-convention](../../../docs/conventions/component-convention.md)의 "표시 항목이 화면마다 갈리면 조각으로 나눠 화면이 조립한다"를 그대로 따라, 총 개수·정렬·카드까지 통째로 두 컴포넌트로 나눴다. 라우트(`/search`, `/search/result`)는 그대로 둔다 — 사고 원인이 라우트 공유가 아니라 컴포넌트 하나에 표시 항목을 다 밀어 넣은 것이었고, `product-compare-view.tsx`가 이미 이 라우트에 `slot` 쿼리로 진입하고 있어 바꾸면 그쪽까지 함께 고쳐야 한다.

**찜 하트는 `home-view`·`recommendations-view`의 흰 하트와 다르게 어두운 원판 위에 얹는다.** Figma(2396-80432)의 사진이 실사라 흰 하트만으로는 배경에 묻힌다. 원판(32px)은 이미지 모서리에서 정확히 4px 떨어져야 한다(2396-80461). 44px 탭 영역을 확보하려고 32px 원판을 더 큰 버튼으로 감싸면, 원판이 그 버튼 안에서 가운데 정렬되며 안쪽으로 밀려 4px이 아니게 된다 — 그래서 원판 자체를 버튼으로 쓰고 `after:` 의사요소로 탭 영역만 44px로 넓힌다(`home-view`의 텍스트 버튼과 같은 기법).

**반대쪽 비교 자리에 이미 있는 상품은 고르기 목록에서 뺀다.** `slot`으로 채우러 온 자리 말고 반대쪽 자리의 현재 상품 id를 `other`(또는 상세 흐름의 `first`) 쿼리로 받아, 같은 상품을 또 고르면 비교 화면에서 두 자리가 같은 id를 가져 React key가 충돌하는 사고를 막는다(`alreadyPicked`, #245).

## 아직 정하지 않은 것

**결과가 0건일 때 추천 상품을 함께 보일지 정해지지 않았다.** 유즈케이스 시트에 "아래에 추천 상품 리스트 표시?"가 물음표와 함께 적혀 있다. 확정 전이라 문구만 둔다.

**목록은 목업이다.** 검색어가 상품명에 들어가는지만 보고 거른다. 실제 검색과 정렬은 서버가 맡을 몫이라 화면에서 다시 `filter`하지 않는다 — 기준은 [AGENTS.md](../../../AGENTS.md)의 2.5절을 본다.
