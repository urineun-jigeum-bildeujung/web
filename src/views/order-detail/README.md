## 라우트

`/mypage/orders/[orderId]` — `src/app/mypage/orders/[orderId]/page.tsx`. 주문·배송 화면 주문 머리의 "주문 상세"가 여기로 온다. 머리말 제목은 시안대로 "주문 내역"이다.

## 2026-09-23 시안 (#405)

회색 바닥(`bg/secondary`) 위에 흰 카드 넷이 8px 간격으로 놓인다. 머리말도 회색 바닥 그대로다.

| 카드 | 그리는 것 |
| --- | --- |
| 첫 카드 | 제목 없이 "결제일 26.09.03"(`payment.paidAt`)과 주문번호. 결제 전 주문이면 결제일 줄을 비운다 |
| 주문 상품 N개 | 상품마다 80px 줄. 금액은 `unitPrice × quantity` |
| 결제상세 | 제목 옆 결제 일시(13px 흐린색), 결제금액·상품 옵션·배송비·결제수단 |
| 배송지 정보 | 항목 이름이 진한 굵은 글씨, 값이 흐린 글씨 |

카드 아래에 "헷갈리는 정보가 있다면 1:1로 자세히 안내해 드릴게요"와 **"1:1문의" 링크(`/mypage/support/inquiries`)**가 오고, 맨 아래에는 배송 전 주문이면 **"주문 취소하기"**, 배송완료 주문이면 **"반품 신청하기"·"교환 신청하기"** 44px 진한 버튼이 붙는다.

## 주문 취소는 여기서 한다 (#410)

`mypa_161_준비중_주문상세`(`3324:37275`) 맨 아래 버튼 → `mypa_161_주문취소_모달`(`3337:49344`). 모달은 "주문을 취소할까요? / 결제하신 금액은 안전하게 환불 처리돼요."에 닫기·빨간 "주문 취소하기"다. **서버가 주문 전체만 취소해서 목록의 상품마다 있던 버튼을 PD팀이 이리로 옮겼다**(2026-09-23). 배송이 시작되기 전(`PAID`·`PREPARING`, 화면의 배송준비중)에만 선다 — 서버 전이 규칙이 그 둘에서만 취소를 받는다.

**보내는 중에는 모달이 닫히지 않는다.** 닫히면 요청만 남아 끝났을 때 취소됐는지 알 수 없다. Escape도 `onOpenChange`로 오는 것을 테스트로 확인해 그 한 곳에서 막는다 — 목록에 있던 코드는 Escape를 따로 한 번 더 막았는데 겹치는 막기였다. 끝나면 문구 표의 `order.cancelled`("주문 취소 완료")를 띄우고 상세를 다시 받아 버튼이 사라진다.

**상태 뱃지를 붙이지 않는다.** 새 시안에서 빠졌다. 반품·교환 신청 상태 뱃지(#334, "반품 수거 중")도 같이 걷었다 — 시안에 자리가 없고, 신청 건을 보일 곳은 목록의 "취소·반품·교환" 탭이다. **탭 화면 시안은 있는데 신청 건을 모아 주는 API가 없어, 그 전까지는 신청 뒤 상태가 어디에도 보이지 않는다.**

**신청할 수 있는 상품이 하나도 없으면 반품·교환 버튼을 감춘다.** 눌러 봐야 신청 화면이 "신청 진행 중"으로 되돌려 보낸다. 끝난 신청(`COMPLETED`·`REJECTED`)만 있으면 다시 신청할 수 있으므로 버튼은 그대로 둔다. 판정은 [entities/order](../../entities/order/README.md)의 `model/claim-status.ts`에 있고 신청 화면도 같은 것을 쓴다.

## 반품·교환은 배송이 끝나야 접수한다

`mypa_161_배송완료`에만 버튼이 그려져 있다. 배송 전에는 주문 취소가 맞는 길이라 그 자리에 "주문 취소하기"가 선다.

**누르면 바로 접수되지 않고 확인창이 한 번 막는다.** 접수하면 기사가 상품을 가지러 오고 그 뒤에야 환불이나 교환이 진행되므로, 무슨 일이 일어나는지 알린 뒤 확인받아야 한다. 되돌릴 수 없는 행동이라 `Dialog`가 아니라 `AlertDialog`를 쓴다.

**반품과 교환은 수거 뒤에 오는 것이 다르다.** 반품은 "바로 환불해 드릴게요", 교환은 "새 상품을 보내드릴게요"다. 시안 문구 그대로다. 확인 버튼은 트리거와 같은 "반품 신청하기"·"교환 신청하기"다.

**확인하면 접수되는 것이 아니라 신청 화면으로 간다.** 기능명세서의 접수에는 사유(단순변심·상품 하자/불량·배송 지연·기타)와 사진이 따라서 확인창에서 바로 서버로 보낼 수 없다. IA도 `MYPA_161_P01`·`P02` 모달 뒤에 `MYPA_261` 작성 화면을 둔다 (#288).

**배송완료 뒤 7일까지만 내보낸다.** 기능명세서와 서버 `Order.isClaimableForReturn`이 같은 규칙이고, `OrderDetailResponse.deliveredAt`으로 `isWithinClaimPeriod`가 판정한다. 화면이 안 막으면 눌러 놓고 접수에서 거절당한다 (#374).

## 클라이언트 컴포넌트다

목록과 같은 이유다. 토큰이 클라이언트 저장소에 있어 서버에서 `Authorization`을 붙일 수 없고, 사람마다 내용이 달라 캐시할 것도 아니다 (AGENTS.md 5.2). 전에는 목 데이터를 쓰느라 서버 컴포넌트였고 `claim-actions.tsx`만 갈라 두었다.

## 신청 화면은 따로 있다

`/mypage/orders/[orderId]/claim`(`views/order-claim`)이 실제 신청 화면이다(#327). 유형은 `?type=return|exchange`로 받는다 — **취소는 이 화면을 거치지 않는다.** PD팀이 2026-09-21에 "취소 버튼 → 모달 → 취소버튼 클릭 시 취소"이고 "사유를 적는 건 반품과 환불만"이라고 확정했다.

**이 화면 시안이 2026-09-23에 완성됐다.** 상품 고르기 → 사유·사진(최대 3장)·상세 사유 → 수거일·요청사항·환불 안내 순이다(`mypa_261`·`mypa_262`·`mypa_361`·`mypa_362`). #408에서 이 세 단계로 교체했다.

## 카드와 줄을 다시 이 화면에 두었다

와이어프레임 때는 `shared/ui`의 `DetailCard`·`DefinitionRow`를 썼는데 UI 시안과 어긋나 되돌렸다 (#205).

**`DetailCard`는 children을 `<dl>`로 감싼다.** 시안의 "주문 상품" 카드에는 이름·값 쌍이 아니라 상품 목록이 들어가는데 `dl`의 자식으로 올 수 없다.

**`DefinitionRow`는 이름 칸이 고정폭(`w-24`)에 타이포가 한 벌이다.** 시안은 자리마다 다르게 쓴다 — 주문번호는 `label/bold_14`와 `body/regular_14`, 결제금액은 `title/bold_16`과 `title/bold_18`, 배송비는 양쪽 다 `body/medium_14`다.

**`paym_002`(결제 완료)에는 카드가 아예 없다.** 흰 바닥에 결제상세·배송지 정보가 그대로 놓인다. 그 화면 작업 때 `DetailCard`의 자리를 다시 본다.

## 결제 내역 줄만 `entities/order`와 함께 쓴다

`paym_002`(주문 완료)가 같은 블록을 쓰려고 `entities/order`로 올렸다 (#210). **2026-09-23 시안부터는 결제 내역 줄(`PaymentDetail`)만 함께 쓴다.** 카드 제목(18px)·결제 일시(13px 흐린색)·배송지 항목 이름(진한 색)이 주문 완료와 달라져, `DetailSection`·`DeliveryDetail`을 고치면 주문 완료까지 바뀐다. 그래서 이 화면이 카드 머리와 배송지 줄을 `DetailRow`로 직접 조립한다 (#405).

## API

`GET /orders/{orderId}`로 받는다. 목록과 달리 배송지·결제 정보가 함께 온다.

**응답에 없어 화면이 만드는 값이 둘이다.**

| 화면에 필요한 것 | 어떻게 만드나 |
| --- | --- |
| 배송비 | `totalAmount - productAmount`. 기능명세서가 3,000원 고정으로 적어 두었고 명세 Example의 차액도 3,000원이다 |
| 배송지 한 줄 | `address`와 `addressDetail`을 이어 붙인다. 시안은 한 덩어리로 보여준다 |

**상품이 여럿이면 모두 그린다.** 목록은 첫 줄만 세우고 나머지를 수로 접지만 상세는 무엇을 샀는지 다 보여야 한다. 줄마다 금액은 `unitPrice × quantity`다 — `unitPrice`는 낱개 값이라 명세 Example의 `productAmount`가 그 합이다.

## 아직 없는 것

**상품 옵션은 없는 것이 맞다.** 시안의 둘째 줄이 그 자리인데 백엔드에 옵션이라는 데이터가 없다. PD팀이 "옵션은 빼고 수량은 있어도 괜찮다"고 확인해 줬다 (#297).

**결제수단 상세.** 시안은 "신한카드 \*\*\*\*-\*\*\*\*-\*\*\*\*-1234"인데 응답의 `payment.method`로는 카드번호를 알 수 없다. PD팀이 **그 자리를 토스페이 로고로 통일**하라고 확정해(#304) 지금은 로고만 놓는다. 백엔드도 2026-09-21에 "수단 이름만 보여주는 쪽으로 정리되어도 좋을 것 같다"고 했지만 **보이는 것은 PD 확정을 따른다.**

**상품별 상태.** 응답에 `itemStatus`가 오지만 쓰지 않는다. 값은 백엔드 `OrderItemStatus`에서 확인했다(`PAID`·`CANCELLED`·`PARTIAL_RETURN`·`RETURNED`). 한 상품만 반품 중인 것을 `claims[]`로 그렸는데(#334) 2026-09-23 시안에서 뱃지 자리가 빠져 걷었다. "취소·반품·교환" 탭 화면이 오면 그때 쓴다.

**반품·교환 접수 화면 시안.** `POST /orders/{orderId}/claims`는 **`views/order-claim`에서 실제로 부른다**(#327). 시안대로 세 단계로 교체했다(#408, 위 "신청 화면" 절).
