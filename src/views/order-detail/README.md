## 라우트

`/mypage/orders/[orderId]` — `src/app/mypage/orders/[orderId]/page.tsx`. 주문·배송 화면 주문 머리의 "주문 상세"가 여기로 온다. 머리말 제목은 시안대로 "주문 내역"이다.

## 2026-09-23 시안 (#405)

회색 바닥(`bg/secondary`) 위에 흰 카드 넷이 8px 간격으로 놓인다. 머리말도 회색 바닥 그대로다.

| 카드 | 그리는 것 |
| --- | --- |
| 첫 카드 | 제목 없이 "결제일 26.09.03"(`payment.paidAt`)과 주문번호. 결제 전 주문이면 결제일 줄을 비운다 |
| 주문 상품 N개 | 상품마다 80px 줄. 금액은 그 줄에 실제로 낸 돈(`amount`) |
| 결제상세 | 제목 옆 결제 일시(13px 흐린색), 결제금액·판매 금액·배송비·결제수단(로고 옆 "Toss Pay"). `PaymentDetail`의 기본 모양이 이 화면이다 (#439) |
| 배송지 정보 | 항목 이름이 진한 굵은 글씨, 값이 흐린 글씨 |

카드 아래에 "헷갈리는 정보가 있다면 1:1로 자세히 안내해 드릴게요"와 **"1:1문의" 링크(`/mypage/support/inquiries`)**가 오고, 맨 아래에는 배송 전 주문이면 **"주문 취소하기"**, 배송완료 주문이면 **"구매확정"·"반품·교환"** 44px 진한 버튼 둘이 한 줄로 붙는다 (#462).

## 구매 확정도 여기서 한다 (#462)

배송완료 상품마다 목록에 있던 "구매확정 하기"를 옮겼다. 서버는 주문 전체만 확정하는데(`POST /orders/{orderId}/confirm`) 상품마다 버튼이 있으면 한 상품만 확정되는 줄 안다. PD팀은 상품별 확정을 바랐지만 서버가 주문 단위라 주문 취소처럼 주문 전체가 보이는 이 자리로 옮겼다(2026-09-28).

**버튼은 둘이다.** 확정을 반품·교환 밑에 더하면 글자 버튼이 셋이 되어, PD팀이 "구매확정"·"반품·교환" 둘로 줄이고 반품과 교환은 누른 뒤 시트에서 고르게 했다(`3610:59567`·`3610:59865`). 반품·교환 기간(7일)이 지나거나 신청할 상품이 없으면 "구매확정"만 한 줄을 채운다.

**확정 시트는 확정할 상품을 모두 보인다.** 확정이 주문 단위라서다. 금액은 위 "주문 상품" 카드와 같은 `amount`다. **보내는 중에는 닫히지 않고**, 끝나면 문구 표의 `order.purchaseConfirmed`를 띄운다. 구매 확정은 `204 No Content`라 바뀐 주문을 응답으로 받지 못해 끝난 뒤 상세를 다시 받는다 — **낙관적으로 먼저 그리지 않는다.** 되돌릴 수 없는 동작이라 서버가 거절하면 확정된 줄 알았던 주문이 되살아난다 (#284). 확정하면 서버가 반품·교환도 닫아(`isClaimableForReturn`은 `DELIVERED`만 받는다) 두 버튼이 함께 사라진다.

## 주문 취소는 여기서 한다 (#410)

`mypa_161_준비중_주문상세`(`3324:37275`) 맨 아래 버튼 → `mypa_161_주문취소_모달`(`3337:49344`). 모달은 "주문을 취소할까요? / 결제하신 금액은 안전하게 환불 처리돼요."에 닫기·빨간 "주문 취소하기"다. **서버가 주문 전체만 취소해서 목록의 상품마다 있던 버튼을 PD팀이 이리로 옮겼다**(2026-09-23). 배송이 시작되기 전(`PAID`·`PREPARING`, 화면의 배송준비중)에만 선다 — 서버 전이 규칙이 그 둘에서만 취소를 받는다.

**보내는 중에는 모달이 닫히지 않는다.** 닫히면 요청만 남아 끝났을 때 취소됐는지 알 수 없다. Escape도 `onOpenChange`로 오는 것을 테스트로 확인해 그 한 곳에서 막는다 — 목록에 있던 코드는 Escape를 따로 한 번 더 막았는데 겹치는 막기였다. 끝나면 문구 표의 `order.cancelled`("주문 취소 완료")를 띄우고 상세를 다시 받아 버튼이 사라진다.

**주문 상태 뱃지를 결제일 줄 끝에 단다(QA No.287, #655).** 2026-09-23 시안에서 빠져 걷었다가 QA가 주문 상태(교환·반품 세부 포함)가 보여야 한다고 해 되살렸다. 취소·환불완료·부분환불도 문구가 있다. 반품·교환 신청이 걸린 상품에는 가장 나중 신청을 "반품 접수"·"교환 검수 중"처럼 종류와 진행 상태로 단다(`claimLabel`, 예전 #334의 자리). 색은 "취소·반품·교환" 탭의 건 뱃지와 같다 — 반품 빨강, 교환 파랑, 취소 회색.

**배송 요청사항 줄은 늘 세운다(QA No.290, #655).** 비어 있으면 "없음"이라 적는다. 전에는 줄을 숨겨(#318) 요청사항이 빠진 것처럼 보였다.

**신청할 수 있는 상품이 하나도 없으면 반품·교환 버튼을 감춘다.** 눌러 봐야 신청 화면이 "신청 진행 중"으로 되돌려 보낸다. 끝난 신청(`COMPLETED`·`REJECTED`)만 있으면 다시 신청할 수 있으므로 버튼은 그대로 둔다. 판정은 [entities/order](../../entities/order/README.md)의 `model/claim-status.ts`에 있고 신청 화면도 같은 것을 쓴다.

## 반품·교환은 배송이 끝나야 접수한다

`mypa_161_배송완료`에만 버튼이 그려져 있다. 배송 전에는 주문 취소가 맞는 길이라 그 자리에 "주문 취소하기"가 선다.

**"반품·교환"을 누르면 시트에서 둘 중 하나를 고른다(#462).** 시트는 "상품에 문제가 생겼나요?" 아래 "반품하기"·"교환하기" 두 줄이고, 줄 모양(44 · 아이콘 28 · 화살표 28)이 공용 `ListRowLink` md와 같아 그것을 쓴다. 아이콘 `refund`·`change`는 PD팀이 이 시트에 더한 것을 세트에 옮겼다.

**예전의 접수 확인 모달은 없다.** 반품·교환 버튼마다 "반품 접수를 진행할까요?" 같은 확인창(`3324:37378`·`3324:36769`)이 있었는데, 시트에서 한 번 고르는 것이 그 자리를 대신해 PD팀이 시안에서 지웠다(2026-09-28).

**고른다고 접수되지 않고 신청 화면으로 간다.** 기능명세서의 접수에는 사유(단순변심·상품 하자/불량·배송 지연·기타)와 사진이 따라서 바로 서버로 보낼 수 없다. 신청 화면에서 상품 고르기 → 사유 → 수거 세 단계를 거친 뒤에야 접수된다 (#288, #408).

**배송완료 뒤 7일까지만 내보낸다.** 기능명세서와 서버 `Order.isClaimableForReturn`이 같은 규칙이고, `OrderDetailResponse.deliveredAt`으로 `isWithinClaimPeriod`가 판정한다. 화면이 안 막으면 눌러 놓고 접수에서 거절당한다 (#374).

## 클라이언트 컴포넌트다

목록과 같은 이유다. 토큰이 클라이언트 저장소에 있어 서버에서 `Authorization`을 붙일 수 없고, 사람마다 내용이 달라 캐시할 것도 아니다 (AGENTS.md 5.2). 전에는 목 데이터를 쓰느라 서버 컴포넌트였고 `claim-actions.tsx`만 갈라 두었다.

## 신청 화면은 따로 있다

`/mypage/orders/[orderId]/claim`(`views/order-claim`)이 실제 신청 화면이다(#327). 유형은 `?type=return|exchange`로 받는다 — **취소는 이 화면을 거치지 않는다.** PD팀이 2026-09-21에 "취소 버튼 → 모달 → 취소버튼 클릭 시 취소"이고 "사유를 적는 건 반품과 환불만"이라고 확정했다.

**이 화면 시안이 2026-09-23에 완성됐다.** 상품 고르기 → 사유·사진(최대 3장)·상세 사유 → 수거일·요청사항·환불 안내 순이다(`mypa_261`·`mypa_262`·`mypa_361`·`mypa_362`). #408에서 이 세 단계로 교체했다.

## 카드와 줄을 다시 이 화면에 두었다

와이어프레임 때는 `shared/ui`의 `DetailCard`·`DefinitionRow`를 썼는데 UI 시안과 어긋나 되돌렸다 (#205).

**`DetailCard`는 children을 `<dl>`로 감싼다.** 시안의 "주문 상품" 카드에는 이름·값 쌍이 아니라 상품 목록이 들어가는데 `dl`의 자식으로 올 수 없다.

**`DefinitionRow`는 이름 칸이 고정폭(`w-24`)에 타이포가 한 벌이다.** 시안은 자리마다 다르게 쓴다 — 주문번호는 `label/bold_14`와 `body/regular_14`, 결제금액은 `title/bold_16`과 `title/bold_18`, 배송비는 양쪽 다 `body/medium_14`다.

**`paym_002`(결제 완료)에는 카드가 아예 없다.** 흰 바닥에 결제상세·배송지 정보가 그대로 놓인다. 그 화면 작업 때 `DetailCard`의 자리를 다시 본다.

## 결제 내역 줄만 `entities/order`와 함께 쓴다

`paym_002`(주문 완료)가 같은 블록을 쓰려고 `entities/order`로 올렸다 (#210). **2026-09-23 시안부터는 결제 내역 줄(`PaymentDetail`)만 함께 쓴다.** 결제 일시(13px 흐린색)·배송지 항목 이름(진한 색)이 주문 완료와 달라져, `DetailSection`·`DeliveryDetail`을 고치면 주문 완료까지 바뀐다. 그래서 이 화면이 카드 머리와 배송지 줄을 `DetailRow`로 직접 조립한다 (#405).

## API

`GET /orders/{orderId}`로 받는다. 목록과 달리 배송지·결제 정보가 함께 온다.

**응답에 없어 화면이 만드는 값이 둘이다.**

| 화면에 필요한 것 | 어떻게 만드나 |
| --- | --- |
| 배송비 | `totalAmount - productAmount`. 기능명세서가 3,000원 고정으로 적어 두었고 명세 Example의 차액도 3,000원이다 |
| 배송지 한 줄 | `address`와 `addressDetail`을 이어 붙인다. 시안은 한 덩어리로 보여준다 |

**상품이 여럿이면 모두 그린다.** 목록은 첫 줄만 세우고 나머지를 수로 접지만 상세는 무엇을 샀는지 다 보여야 한다. 줄마다 금액은 서버가 준 `amount`(실제로 낸 단가 `paidUnitPrice` × 수량)이고, 줄을 모두 더하면 `productAmount`다. **`unitPrice`는 할인 전 단가라 곱해 쓰지 않는다** — 그렇게 세던 때는 할인된 상품의 줄 금액이 결제 금액보다 크게 보였다(백엔드 sever#170로 두 값이 생김, #516).

## 아직 없는 것

**상품 옵션은 없는 것이 맞다.** 시안의 둘째 줄이 그 자리인데 백엔드에 옵션이라는 데이터가 없다. PD팀이 "옵션은 빼고 수량은 있어도 괜찮다"고 확인해 줬다 (#297).

**결제수단 상세.** 시안은 "신한카드 \*\*\*\*-\*\*\*\*-\*\*\*\*-1234"인데 응답의 `payment.method`로는 카드번호를 알 수 없다. PD팀이 **그 자리를 토스페이 로고로 통일**하라고 확정했고(#304), QA가 결제수단이 글자로 보여야 한다고 해 로고 옆에 "Toss Pay"를 적는다(QA No.288, #655). 서버의 `payment.method`는 늘 "토스페이먼츠"라 쓰지 않는다.

**상품별 상태.** 응답에 `itemStatus`가 오지만 쓰지 않는다. 값은 백엔드 `OrderItemStatus`에서 확인했다(`PAID`·`CANCELLED`·`PARTIAL_RETURN`·`RETURNED`). 신청 상태는 `itemStatus`가 아니라 `claims[]`로 단다(위 "주문 상태 뱃지", #655).

**반품·교환 접수 화면 시안.** `POST /orders/{orderId}/claims`는 **`views/order-claim`에서 실제로 부른다**(#327). 시안대로 세 단계로 교체했다(#408, 위 "신청 화면" 절).
