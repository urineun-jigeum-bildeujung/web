# views/order-detail

주문 하나의 내역을 자세히 보여주는 화면. UI 시안 `mypa_161`·`mypa_161_배송완료`에 대응한다.

| 파일 | 설명 |
| --- | --- |
| `ui/order-detail-view.tsx` | 주문정보·결제상세·배송지 정보 세 카드를 조립한다 |
| `ui/order-detail-skeleton.tsx` | 불러오는 동안의 뼈대 |
| `ui/order-detail-view.test.tsx` | 카드 구성, 계산해 만드는 값, 반품·교환 접수 조건과 신청 상태 표시를 본다 |
| `ui/claim-actions.tsx` | 배송완료 주문의 반품·교환 버튼과 확인창 |
| `index.ts` | 공개 API |

## 라우트

`/mypage/orders/[orderId]` — `src/app/mypage/orders/[orderId]/page.tsx`. 주문·배송 화면의 "자세히 보기"가 여기로 온다.

## 신청한 뒤의 상태도 보인다

`items[].claims[]`가 실려 오므로 **그 상품 줄에 "반품 수거 중"처럼 붙인다** (#334). 시안(`mypa_161_배송완료`)은 버튼까지만 그리고 신청한 뒤는 그리지 않아, 새 모양을 만들지 않고 주문 상태 뱃지와 같은 것을 쓴다.

**주문 뱃지는 첫 줄에만, 신청 뱃지는 걸린 줄마다 붙는다.** 앞은 주문 단위 상태고 뒤는 실제로 상품별이다 — 두 상품 중 하나만 반품 중일 수 있다.

**신청할 수 있는 상품이 하나도 없으면 반품·교환 버튼을 감춘다.** 눌러 봐야 신청 화면이 "신청 진행 중"으로 되돌려 보낸다. 끝난 신청(`COMPLETED`·`REJECTED`)만 있으면 다시 신청할 수 있으므로 버튼은 그대로 둔다.

판정과 문구는 [entities/order](../../entities/order/README.md)의 `model/claim-status.ts`에 있다. 신청 화면도 같은 것을 쓴다.

## 반품·교환은 배송이 끝나야 접수한다

`mypa_161_배송완료`에만 버튼이 그려져 있다. 배송 전에는 주문 취소가 맞는 길이라 그 상태에서는 자리를 만들지 않는다.

**누르면 바로 접수되지 않고 확인창이 한 번 막는다.** 접수하면 기사가 상품을 가지러 오고 그 뒤에야 환불이나 교환이 진행되므로, 무슨 일이 일어나는지 알린 뒤 확인받아야 한다. 되돌릴 수 없는 행동이라 `Dialog`가 아니라 `AlertDialog`를 쓴다.

**반품과 교환은 수거 뒤에 오는 것이 다르다.** 반품은 "바로 환불해 드릴게요", 교환은 "새 상품을 보내드릴게요"다. 시안 문구 그대로다.

**확인하면 접수되는 것이 아니라 신청 화면으로 간다.** 기능명세서의 접수에는 사유(단순변심·상품 하자/불량·배송 지연·기타)와 사진이 따라서 확인창에서 바로 서버로 보낼 수 없다. IA도 `MYPA_161_P01`·`P02` 모달 뒤에 `MYPA_261` 작성 화면을 둔다 (#288).

**7일 조건은 아직 못 건다.** 기능명세서는 "배송완료 후 7일 이내"에만 버튼을 띄우라고 하는데 응답에 배송완료 시각이 없다. 지금은 배송완료 상태 전체에 내보내고 백엔드에 확인을 요청해 뒀다.

## 클라이언트 컴포넌트다

목록과 같은 이유다. 토큰이 클라이언트 저장소에 있어 서버에서 `Authorization`을 붙일 수 없고, 사람마다 내용이 달라 캐시할 것도 아니다 (AGENTS.md 5.2). 전에는 목 데이터를 쓰느라 서버 컴포넌트였고 `claim-actions.tsx`만 갈라 두었다.

## 신청 화면은 라우트만 있다

`/mypage/orders/[orderId]/claim`(`views/order-claim`)은 자리 표시 화면이다. 유형은 `?type=cancel|return|exchange`로 받는다.

**Figma에 이 화면 시안이 없다.** 2026-09-21에 파일 전체를 검색해 `사유`·`단순변심`이 한 건도 없는 것을 확인했고, PD팀 답도 "우선순위 낮음"이다. 시안이 오기 전에는 채우지 않는다.

## 카드와 줄을 다시 이 화면에 두었다

와이어프레임 때는 `shared/ui`의 `DetailCard`·`DefinitionRow`를 썼는데 UI 시안과 어긋나 되돌렸다 (#205).

**`DetailCard`는 children을 `<dl>`로 감싼다.** 시안의 주문정보 카드에는 주문번호 쌍 옆에 상품 줄과 반품·교환 버튼이 함께 들어가는데 둘 다 `dl`의 자식으로 올 수 없다.

**`DefinitionRow`는 이름 칸이 고정폭(`w-24`)에 타이포가 한 벌이다.** 시안은 자리마다 다르게 쓴다 — 주문번호는 `label/bold_14`와 `body/regular_14`, 결제금액은 `title/bold_16`과 `title/bold_18`, 배송비는 양쪽 다 `body/medium_14`다.

**`paym_002`(결제 완료)에는 카드가 아예 없다.** 흰 바닥에 결제상세·배송지 정보가 그대로 놓인다. 그 화면 작업 때 `DetailCard`의 자리를 다시 본다.

## 결제상세·배송지 블록은 `entities/order`에 있다

`paym_002`(주문 완료)가 같은 블록을 써서 올렸다 (#210). 카드 껍데기는 `DetailSection`이 갖지 않으므로 이 화면이 `className="rounded-xl bg-card px-3 py-4"`로 얹는다.

## API

`GET /orders/{orderId}`로 받는다. 목록과 달리 배송지·결제 정보가 함께 온다.

**응답에 없어 화면이 만드는 값이 둘이다.**

| 화면에 필요한 것 | 어떻게 만드나 |
| --- | --- |
| 배송비 | `totalAmount - productAmount`. 기능명세서가 3,000원 고정으로 적어 두었고 명세 Example의 차액도 3,000원이다 |
| 배송지 한 줄 | `address`와 `addressDetail`을 이어 붙인다. 시안은 한 덩어리로 보여준다 |

**상품이 여럿이면 모두 그린다.** 목록은 첫 줄만 세우고 나머지를 수로 접지만 상세는 무엇을 샀는지 다 보여야 한다. 줄마다 금액은 `unitPrice × quantity`다 — `unitPrice`는 낱개 값이라 명세 Example의 `productAmount`가 그 합이다.

## 아직 없는 것

**상품 옵션은 없는 것이 맞다.** 시안의 둘째 줄이 그 자리인데 백엔드에 옵션이라는 데이터가 없다. PD팀이 "옵션은 빼고 수량은 있어도 괜찮다"고 확인해 줬다 (#297).

**결제수단 상세.** 시안은 "신한카드 \*\*\*\*-\*\*\*\*-\*\*\*\*-1234"인데 응답의 `payment.method`로는 카드번호를 알 수 없다. PD팀이 **그 자리를 토스페이 로고로 통일**하라고 확정해(#304) 지금은 로고만 놓는다.

**상품별 상태.** 응답에 `itemStatus`가 오지만 값 목록을 알지 못해 쓰지 않는다. 한 상품만 반품 중인 주문을 그리려면 이것이 필요하다.

**반품·교환 접수.** `POST /orders/{orderId}/claims`는 열렸지만 신청 화면 시안이 없어 부를 자리가 없다.
