# views/recommendations

고른 아이에게 맞는 상품을 모아 보여준다. UI 시안 `#273`(1576-87320)에 대응한다.

| 파일 | 설명 |
| --- | --- |
| `ui/recommendations-view.tsx` | 맞춤 추천 |
| `ui/recommendations-view.test.tsx` | 적합도가 문장으로도 읽히는지, 아이를 고를 수 있는지(실제 목록·기본 아이·아이 없음), 분류를 요청에 싣는지, 네 정렬이 각각의 순서를 내는지, 추천 결과(성공·빈 목록·실패·감점·품절)를 어떻게 그리는지, 실패 뒤 분류를 바꾸면 다시 부르는지, 카드 하트가 서버 찜을 따르고 뒤집는지, 헤더에 알림·장바구니가 있는지 본다 |

## 라우트

```text
/recommendations?pet=<아이 id>&category=<all|food|snack|supplement>&sort=<recommend|latest|rating-high|rating-low>
```

어느 아이 기준인지, 어떤 분류로 걸렀는지, 어떤 기준으로 정렬했는지를 주소에 남긴다. 상품 상세로 갔다 돌아와도 조건이 유지되어야 한다.

메인 화면의 "맞춤 추천" 섹션 "더보기"를 눌러 들어오는 서브 화면이다. 시안 헤더는 홈 화면과 같은
로고형(뒤로가기 없음)이지만, 이 화면은 바텀내비 탭 루트가 아니라 더보기로 들어가는 서브 화면이라
사용자 흐름상 뒤로 갈 방법이 있어야 한다고 판단해 `PageHeader`(뒤로가기+제목)를 그대로 두었다.
시안대로 바꿀지는 확정하지 않았고 프디팀 확인이 필요하다(자세한 내용은 개인 QA 기록 참고, #273).
**오른쪽 검색·알림·장바구니는 시안대로 둔다** — 빠져 있어 QA 1차에서 잡혔다(#470). 메인 헤더와 같은 순서·아이콘이고, 알림·장바구니는 같은 위젯(`widgets/notification-bell`·`widgets/cart-link`)이다.

## 아이는 실제 목록이다

마이페이지와 같은 `GET /members/me/pets` 목록에서 고른다(#470). 예시 아이(코코·봄이)를 쓰던 동안 화면마다 이름이 달랐다. 주소의 `?pet=`이 없거나 목록에 없으면 기본 아이 기준이다. **고른 아이가 대표(기본) 아이가 된다(QA HM-059, #657)** — 메인과 같은 훅(`entities/pet`의 `useSelectDefaultPet`)으로 서버에 기본 아이 변경을 보내고, 받은 뒤에 "대표 아이가 ○○(으)로 바뀌었어요"를 띄우며, 실패하면 원래 기본 아이로 되돌린다. 주소만 바꾸던 동안에는 드롭다운 순서가 그대로이고 다른 화면에 가면 처음 아이로 돌아갔다. 메인의 "더보기"는 고른 아이를 `?pet=`으로 들고 온다. 로그인하지 않았으면 목록을 부르지 않고 "우리 아이의 건강 고민을 덜어줄"로 읽는다. 로그인 여부를 아직 모르는 동안(서버 렌더·하이드레이션)은 받는 중과 같이 알약 자리를 뼈대로 잡는다.

## 상품은 AI 추천 API다(#600)

고른 아이로 `entities/recommendation`의 `useQueryHomeRecommendations`(`POST /recommend/home`, AI팀 명세 v3.0.0)를 부른다. 명세와 다른 값(분류·점수·상태·단가·알레르기)을 어떻게 바꿔 쓰는지는 [entities/recommendation](../../entities/recommendation/README.md)에 있다.

- **분류는 서버가 거른다.** 탭을 바꾸면 `category`(간식은 `treat`)를 실어 다시 부른다. 전체는 분류를 보내지 않는다
- **정렬은 받은 목록 안에서 FE가 한다 — AGENTS 2.5의 예외다.** 추천 API의 정렬이 추천순 하나뿐이라 최신순(`created_at`)·별점순(`rating`)을 요청할 수 없다. 그래서 한 번에 받을 수 있는 최대(`size: 50`)를 받고, 추천순은 서버 순서(`rank`) 그대로다. 50개 밖의 상품은 어느 정렬에서도 보이지 않는다 — 서버가 정렬을 지원하면 요청으로 옮긴다
- **카드는 적합도·판매 상태 배지·단가·별점·추천 이유를 보인다.** 시안(1585-16763)의 "하루 예상 급여비 약 N원"은 하루 급여량이 응답에 없어 그리지 못하고, 메인 시안의 단가 줄("1g당 19원")을 쓴다. 해석하지 못하면 그 줄을 비운다. 별점은 후기 수로 가른다(후기가 없으면 회색 별에 "-")
- **알레르기 성분과 겹쳐 감점된 상품도 남는다.** "등록한 알레르기 성분이 들어 있어요" 한 줄을 붙이고 성분 코드는 보이지 않는다. 품절은 카드를 흐리고 "품절" 배지를 얹으며, 재입고 알림은 상품 상세가 맡는다
- **추천만 실패하면 격자만 알린다.** 머리말·아이 알약·분류·정렬은 남고 "다시 시도"가 조회를 리셋한다. 받는 동안은 격자 뼈대다. 로그인하지 않았거나 아이가 없으면 부르지 않고 무엇을 하면 되는지 알린다
- 아이 이름은 응답의 `pet_name`이 아니라 아이 목록의 이름이다

## 찜은 서버에 남는다(#611)

카드 하트는 `features/toggle-wishlist`로 서버 찜에 잇는다. 찜 여부는 전체 찜 목록(`useWishedProductIds`)에서 오고, 누르면 `useToggleWishlist`가 서버에서 뒤집는다. 찜 목록 캐시를 먼저 바꿔 하트가 곧바로 바뀌고, 좋아요 탭·메인·검색 결과의 하트와 같은 캐시라 어디서 찜해도 함께 바뀐다. 전에는 화면 상태(`useState`)라 서버에 가지 않고 새로고침하면 사라졌다(QA r36). 담으면 상품 상세와 같은 "해당 상품을 찜 목록에 담았어요!"를 띄운다(QA r35, #625).

- **모양은 이 화면 시안대로 둔다.** 다른 목록의 `CardHeartButton`(어두운 원판 + 흰 하트)이 아니라 흰 원판 위 회색·주황 하트라, 버튼은 이 화면이 그리고 동작만 같게 한다
- **찜 목록을 받는 동안은 하트를 막고 그 자리에 대기를 보인다.** PATCH가 토글이라 모르는 채로 누르면 이미 찜한 상품의 찜이 서버에서 지워진다(#493 리뷰)

## 이 화면이 하는 말

**"보호자님이 알려주신 건강 고민을 바탕으로 추천해요"**를 화면에 적는다. 별점·인기순 나열과 갈라지는 지점이라, 무엇을 근거로 골랐는지 보이지 않으면 이 화면의 의미가 없다.

적합도는 숫자만 두지 않고 구간 문구를 함께 노출한다. 92라는 값만으로는 높은지 낮은지 판단을 사용자에게 떠넘기게 된다.

## 아직 없는 것

- 적합도 배지(`entities/product`의 `MatchScoreBadge`)는 home-view와 같이 쓰는 공용 컴포넌트라 이번 이슈(#273)에서 손대지 않았다.
  시안(1584-16064 등)은 이 화면 안에서도 점수 구간별로 배지 배경색이 다르게 보이는데다, **Figma에 이 배지를 다른 화면 표기와 통일할
  예정이라는 코멘트가 달려 있다.** 지금 배지 표기(단일 브랜드색 배경, "적합도 N점" 문구)를 그대로 두고, 어떻게 통일할 계획인지
  프디팀에 확인하기로 했다 — 정확한 색상값도 이번 조회로는 못 받았고, 확정 방향도 모르는 채로 임의로 바꾸면 다시 바꿔야 할 수 있다
- 정렬 4개(추천순·최신순·별점 높은순·별점 낮은순) 중 서버가 계산하는 것은 추천순뿐이다. 나머지는 받은 50개 안에서만 정렬한다(위 "상품은 AI 추천 API다")
- 건강 고민 칩(관절·알러지·구강관리)이 이번 시안(#273)에서 상품 분류 탭(전체·사료·간식·영양제)으로 바뀌었다. 분류는 추천 API가 거르지만, 아이가 등록한 고민별로 거르는 요청은 명세에 없다
- 찜 버튼 원판 배경색이 시안(불투명 흰색)과 다르다. 이 프로젝트에 완전 불투명 흰색 surface 토큰이 없어, 사진 위에 흰 원판을 얹는 같은 목적으로 이미 쓰이던 `surface-overlay-static`(흰색 70/50% 반투명)을 근사로 썼다
- 하단 네비게이션(`BottomNav`)이 시안과 상태가 다르다. 시안은 "홈" 탭이 켜진 채로 그려져 있는데, 이 화면은 `BottomNav`가 아는 네 경로(`/`, `/compare`, `/likes`, `/mypage`) 어디에도 속하지 않아 실제로는 어느 탭도 켜지지 않는다. 헤더와 같은 "이 화면이 어느 탭 소속인가" 문제라 프디팀 확인이 필요하다
