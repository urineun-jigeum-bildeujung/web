# views/likes

찜한 상품·최근에 본 상품·자주 산 상품을 탭으로 나눠 본다. 찜 탭은 UI 시안(`#274`, 1117-4972, 빈 상태 2022-158710)에 대응하고 실제 API로 연동했다(#390). "최근에 봤어요"는 백엔드 API가 없어 이 브라우저에 남긴 기록으로 연다(#509, 팀장 결정). "자주 샀어요"는 PD 확인 결과 이번 MVP 범위 밖이라 탭은 남겨두고 눌러도 반응하지 않으며 여전히 목데이터다(#274 QA 답변).

| 파일 | 설명 |
| --- | --- |
| `model/category.ts` | 찜 탭 카테고리 칩의 URL 값·라벨. API 매핑은 `entities/product`가 갖고 있다(#390) |
| `ui/likes-view.tsx` | 좋아요 세 탭 (찜 탭은 확정 시안·실제 API, 최근에 봤어요는 `recent-tab.tsx`, 자주 샀어요는 비활성·목데이터) |
| `ui/recent-tab.tsx` | "최근에 봤어요" 탭. 브라우저에 남긴 상품 번호(`features/recently-viewed`)를 상품 상세 조회로 그리고, X로 빼고 하트로 찜한다 (#509) |
| `ui/recent-tab.test.tsx` | 최신순·빼기·찜·빈 상태·받는 중·없어진 상품·실패, 서버 렌더에서 빈 상태를 먼저 말하지 않는지 |
| `ui/likes-view.test.tsx` | 탭마다 무엇이 붙는지, 찜 탭이 카테고리별로 서버에서 목록을 받아오는지, 찜 해제 낙관적 갱신·실패 복구를 본다 |

## 라우트

```text
/likes?tab=liked&category=all|food|snack|supplement
```

하단 이동 줄의 "좋아요"가 여기로 온다. 찜 탭의 카테고리를 주소에 남겨 상품 상세에 갔다 돌아와도 보던 자리가 유지되게 한다. `category`는 `/recommendations`와 같은 값 체계다.

`tab`은 `liked`·`recent` 둘만 받는다. 자주 샀어요는 탭 UI만 있고 `?tab=often`처럼 주소로 직접 넣어도 `liked`로 떨어진다 — 탭 클릭만 막으면 주소로는 비활성 탭에 들어가 지우기 동작을 쓸 수 있었다(CodeRabbit 지적, PR #285). `/mypage/recently-viewed`는 `?tab=recent`로 보낸다(#509).

## 헤더는 로고형이다

시안에 뒤로가기형(`1117:4972`)과 로고형(`2022:158710`) 두 장이 함께 있어 #274에서는 뒤로가기형을 따랐다. **PD팀이 로고형으로 확정했다**(2026-09-29). 홈·마이페이지와 같은 바텀내비 탭 첫 화면이라 같은 `PageHeader leading="logo"`에 검색·알림·장바구니를 둔다 (#513).

## 탭마다 카드에 붙는 것이 다르다

| 탭 | 이미지 위 | 이미지 안 | 카드 아래 |
| --- | --- | --- | --- |
| 찜했어요 | 흰 원판+채워진 하트(누르면 바로 풂), 사진 오른쪽 위(4px) | — | — |
| 최근에 봤어요 | X(오른쪽 위)·찜 하트(오른쪽 아래) — 와이어프레임 717:4385 | — | — |
| 자주 샀어요 | 지우기 | 구매 횟수·마지막 구매 | 장바구니·구매하기 |

`shared/ui/product-grid-card`가 이 자리들을 슬롯으로 받는다. 화면 수만큼 boolean을 늘리는 대신 무엇을 놓을지 넘긴다. 찜 탭만 `imageActionClassName`으로 자리를 사진 오른쪽 위 4px로 옮긴다(공용 기본값은 12px) — 나머지 두 탭은 확정 시안이 없어 공용 기본 위치를 그대로 둔다.

## 찜 탭은 카테고리로 거른다

시안(1117-4972)의 칩은 "전체"·"사료"·"간식"·"영양제"다(PD가 알림 상태에서 카테고리로 바꿨다, #274 QA 답변). `shared/ui/filter-chips`를 그대로 재사용한다(36px 알약·고른 것만 `bg-primary`가 시안값과 정확히 일치).

**거르기는 서버가 한다(#390).** 찜 응답에 상품의 카테고리가 없어 프론트에서 다시 거를 수 없다 — `entities/wishlist`의 `useQueryWishlist`를 카테고리 있음·없음 두 번 부른다. 전체 조회는 "찜 전체가 비었는지"를 알려고 항상 켜 두고, 카테고리 조회는 `all`이 아닐 때만 켜서 같은 요청을 두 번 보내지 않는다.

## 아직 없는 것

- "장바구니"와 "구매하기"가 그 화면으로 가기만 하고 고른 상품을 함께 넘기지 못한다. 장바구니의 "결제하기"와 같은 수준이며, 화면 간 전달은 라우터 구조가 정해진 뒤에 붙인다
- "자주 샀어요"는 여전히 목데이터다(MVP 범위 밖, 아래 절)

## 최근에 봤어요는 브라우저에 남긴 기록이다 (#509)

**백엔드에 최근 본 상품 API가 없다**(2026-09-29 Notion API 명세 77줄·백엔드 소스 확인). 팀장 결정으로 프론트가 상품 상세에 들어올 때마다 이 브라우저에 기록한다(`features/recently-viewed`, Zustand `persist`). 기준은 PRD "최근 본 상품 조회"(최신순, 대표 이미지·상품명·판매가·할인율·정가, 찜하기·삭제)와 와이어프레임 명세(73:2245, 최대 9개)다.

- **기록은 상품 번호뿐이다.** 카드 값은 상품 상세 조회(`useQueryProductDetails`)로 받는다 — 서버 값을 Zustand에 복사하지 않는다(AGENTS 5.1)
- **저장된 목록을 읽기 전에는 뼈대를 그린다.** 서버에는 localStorage가 없어 서버 HTML은 목록을 모른다. 곧바로 빈 상태를 그리면 기록이 있는 사람에게 "없어요"가 스친다
- **없어진 상품(404)은 기록에서도 뺀다.** 404가 아닌 실패로 하나도 못 받으면 실패 코드에 맞는 문구(`APP_MESSAGE`)와 다시 시도를 보인다
- **일부만 실패하면 받은 것만 보인다.** 실패한 칸은 알리지 않고 빠지며, 탭에 다시 들어오면 다시 부른다. 한 번 받아 둔 상품은 뒤이은 재조회가 실패해도 카드를 그대로 둔다
- **저장을 막은 브라우저에서도 화면은 돈다.** 사이트 데이터 차단·용량 초과면 기록만 남지 않는다. 저장된 값은 번호가 맞는지 한 칸씩 확인해 옮긴다(code-convention "React 밖의 것 읽기")
- **X는 확인 없이 바로 뺀다.** PRD가 "[터치] 목록에서 제거"라고만 적었다
- 기록은 기기마다 따로다. 로그인 계정과 묶지 않는다

## 자주 샀어요는 탭도 주소도 막혀 있다

PD 확인 결과 이번 MVP 범위 밖이다(#274 QA 답변). 탭 자체는 시안대로 남겨두고 `TabsTrigger`에 `disabled`만 준다. `tab` 쿼리도 받지 않아 `?tab=often`처럼 주소로 직접 들어와도 우회할 수 없다 — 목록·지우기 로직은 코드에 남아 있지만 어느 경로로도 도달할 수 없는 상태다.

찜한 상품 중 고른 카테고리에만 상품이 없을 때는 "이 카테고리엔 담아둔 상품이 없어요"로, 찜한 상품 자체가 없을 때는 "아직 담아둔 상품이 없어요"로 문구를 나눈다 — 둘 다 확정 시안은 없다.

## 찜 탭의 하트는 확인 없이 바로 풀린다

찜 목록엔 한 번에 여러 개를 취소하는 기능이 없어 하나씩 눌러야 하는데, 그때마다 확인 모달·토스트가 뜨면 오히려 방해된다는 PD 판단이다(#274 QA 답변). 하트를 누르면 확인창 없이 바로 목록에서 빠진다 — `entities/wishlist`의 `useMutateWishlist`가 낙관적으로 먼저 캐시에서 빼고, 실패하면 되돌린다(#390).

자주 샀어요 탭의 지우기(X)는 여전히 확인창(`AlertDialog`)을 거친다 — 이 확인창 자체는 확정 시안이 없어 문구·버튼 구성은 기존 와이어프레임 그대로다. 최근에 봤어요의 X는 위 절대로 확인 없이 뺀다.
