`$ARGUMENTS`에 라이브러리가 필요한지 판단한다. `docs/conventions/library-convention.md`를 따르며 아래는 그 실행 절차다.

**설치까지 하지 않는다.** 판단과 근거를 보고하고 사용자의 결정을 받는다.

## 1. 이미 되는지 먼저 본다

순서대로 확인하고, 되는 지점이 나오면 거기서 멈춘다.

1. **`package.json`** — 설치된 것으로 되는가
2. **shadcn** — 제공하는 컴포넌트인가. 제공하면 `npx shadcn add <컴포넌트>`로 받고 의존 패키지는 손으로 설치하지 않는다
3. **플랫폼 기능** — `Intl.NumberFormat`(통화·숫자), `Intl.RelativeTimeFormat`(상대 시간), `IntersectionObserver`(무한 스크롤), `Canvas`(이미지 처리), `structuredClone`. 브라우저가 하는 일에 라이브러리를 얹지 않는다
4. **Next.js 내장** — `node_modules/next/dist/docs/`를 찾아본다. 번들 분석처럼 이미 들어 있는 기능이 있다
5. **검토 이력** — `library-convention.md`의 "겪은 사례" 표에 이미 판단한 것이 있는지 본다

## 2. 후보를 조사한다

후보마다 돌린다.

```bash
npm view <패키지> version peerDependencies time.modified license
```

확인할 것이다.

- **최종 배포일** — 1년 이상 조용하면 이유를 찾는다
- **peerDependencies가 React 19를 받는가** — `^18`만 있으면 설치돼도 동작을 보장하지 않는다
- **Turbopack에서 동작하는가** — 우리 빌드는 Turbopack이다. **Webpack 플러그인은 무동작이다.** 문서 대부분이 Webpack 기준이라 여기서 자주 걸린다
- **커스텀 가능한가** — 자체 UI를 통째로 띄우는지, 데이터만 주고 화면은 우리가 그리는지
- 라이선스

## 3. 도입 기준에 대본다

넷을 모두 만족해야 넣는다. 하나라도 어긋나면 그 사실을 보고한다.

1. 여러 곳에서 되풀이되는가
2. 직접 만들면 위험한가 (접근성·결제·인증)
3. 유지되고 있는가
4. 걷어내기 쉬운가

## 4. 보고한다

| 항목 | 내용 |
| --- | --- |
| 결론 | 필요 없음 / 후보 있음 / 직접 만들기 |
| 근거 | 위 1~3에서 확인한 것 |
| 후보 비교 | 둘 이상이면 표로. 버전·최종 배포일·React 19·커스텀 여부 |
| 설치 위치 | `dependencies` / `devDependencies`와 이유 |
| 설치 명령 | 사용자가 승인하면 바로 쓸 수 있게 |

**넣지 않기로 한 후보는 이유를 함께 남긴다.** 검색하면 제일 먼저 나오는 것들이라, 적어두지 않으면 다음에 같은 후보를 다시 들고 오게 된다.

승인을 받아 설치했다면 갱신할 곳을 알린다 — `AGENTS.md` 기술 스택 표(기준일 포함), `README.md`(런타임 스택만), `CHANGELOG.md`, 팀 Notion 라이브러리 문서.
